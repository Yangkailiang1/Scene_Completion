# 场景生成

输入规范模型、原始需求/设计文档及可选 SSD manifest，使用共享 CLI 的 scene-pipeline。
生成主成功、可选、需求明确异常和全部候选，不等待 scene-review 或 LLM 审查。
候选应带稳定 ID、关注点、SSD 引用、主流程锚点、来源与补充章节。
无明确依据的响应、恢复、参数上限使用待需求确认，不为增加覆盖率读入检查器结果。

先用 prepare-generator-model 从独立的原始需求和设计构建生成输入；使用 ECNU 语义
worker 分包抽取具体条件和全部直接依赖，结果必须带准确原文引用。仅有场景名称不足：
记录检查对象、操作、失败条件、步骤锚点、实际处理和恢复。接口字段、资源归属、
合法状态、库存/数量关系、幂等键、版本、事件时间和调用失败应实例化到对应检查位置。

生成 constraints 不读取 C：既提取已描述异常条件，也从正常校验规则识别其不满足情形；
明确标注引用和关注点。取消/中止使用流程中断关注点；内部依赖失败与外部服务不可用
分别挂到实际调用。源文没有响应/恢复时写待需求确认，不把错误码目录扩写成业务事实。

不同文档中的异常条件分别保留，并逐项记录条件和结果的原文依据。只有对象、操作、
失败机制和结果均一致，才能将需求与设计的分支合并。约束 A 与约束 B 不得写成
“即”“等价于”或合取条件，除非原文明示等价；时序相对不同参照点尤其需要区分。
需求分支已有处理而设计分支规定另一种触发时，保留两条场景，不能用设计细节改写
需求触发条件。未明确冲突的额外设计步骤也应保留独立来源。

正常流程中的每项校验以及全部分支（包括成功返回的重复请求和其他可选分支）
都要提取相应的失败/异常条件约束。幂等检查必须明确业务操作、键、重复条件与
原文处理；幂等返回成功仍是重复条件下的异常候选，不得因 HTTP 成功或可选分类
漏掉关注点实例。不同资源写入、查询、状态更新不能代替业务请求的幂等约束。

显式分支只保留到分歧点之前真实完成的成功前缀，再接分支行为；支付取消不能包含
支付成功步骤。主成功的前后置条件为上下文，不能冒充异常保证。全部明确分支、
约束实例化场景及泛化候选分别标注生成来源；工具不按适用性审查删除候选。

新协议、批次和输出见 ../scene-check/references/three_roles.md。本 Skill 不调用其他 Skill。
