# 五类业务服务的统一判别规则

这五类是既有框架中的功能分类，不是异常集合。抽取器和来源检查器必须使用同一规则。分类只取当前交互的同层正常／普通可选原文行为，不从异常、测试、服务名称或下层分类反推。一个服务可以承担多类职责，但每次交换只挂载这次实际执行的职责。

| 编码 | 中文职责与正向依据 | 原框架关注点 | 不足以成立的依据 |
|---|---|---|---|
| display_interaction | 展示交互：将内容呈现给用户，或明确加工用于用户呈现的结构。正例：展示检索结果、转换展示结构、呈现操作成功提示。 | 显示正确性、渲染性能、设备适配性 | 仅 HTTP 返回、内部保存状态、传递协议字段，不能自动推定 UI 展示。设备／渲染特征未知应保留待确认，不能虚构设备。 |
| query_retrieval | 查询检索：读取、检索已存在的资源或状态。正例：按筛选条件读取记录、查询资源详情。 | 资源存在性、结果正确性、数据可见性 | 只有资源名称或参数校验，不证明执行了查询；读取也不证明发生写入。 |
| resource_mutation | 资源变更：创建、修改、删除资源或持久化其状态。正例：更新记录、创建资源、保存配置。 | 业务约束、持久化一致性、并发与幂等性 | 仅读取、计算或返回一个值，不能自动推定持久化副作用。 |
| analysis_generation | 分析生成：以分析、评估、生成新的业务内容／结论为任务。正例：生成诊断报告、提取记忆、分析异常原因、生成建议。 | 处理正确性、执行时限、资源消耗 | 普通参数／权限／状态／金额校验、DTO 转换、协议解析、比较现有值或汇总列表，不因此成为分析生成。这些规则绑定到实际业务交互，不能仅因有计算就新增分析职责。 |
| release_activation | 发布生效：明确发布／激活版本、配置或资源，使其进入已发布／生效生命周期。正例：发布配置、使新版本生效、修改后重新发布。 | 发布前置条件、发布结果一致性、失败恢复 | 任意写库、外部调用、支付、退款或发货不自动属于发布生效；必须有本层发布／激活生命周期依据。 |

RR 职责必须有本层正常行为引句，并映射到该 RR 请求下真实执行同一职责的 SR 交换；不能仅凭已有 SR 分类复制。SR 分类及 operation_kinds 也必须分别有实际行为依据。显示／处理结果通常属于已有交换的返回或本地步骤，不因分类而新建一次请求。数据库资源读写按已有 SR 资源服务建模，不因此新增业务用例。

来源检查应审查五类的存在和缺失。没有依据的类别应明确判为不适用并说明原因；有真实职责但模型遗漏时，记录原文和缺失映射。不得为了填满五类、减少漏报或消除审计问题而强行分类。分类改变不删减框架的关注点注册，也不审核／删除生成异常候选。
