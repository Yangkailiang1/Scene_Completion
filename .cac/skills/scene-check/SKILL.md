# 场景检查

分别独立读取 RR、SR 原始 spec 和统一关注点注册表，抽取原文明示的原子异常 C_RR、C_SR。
不读取 G 或 test_spec。IR=RR；SR 中 AR 描述仅为追溯，不建立 AR 集合。
复合分支中不同对象或失败机制拆分。正常与普通可选流程不进入C；主动取消、主动退出等正常用户选择属于可选，不因cancellable或扩展路径位置而认定异常。成功返回的重复请求等真实异常条件仍可保留。文档标签与已确认业务意义冲突时先记录原文依据并确认文档修正，再建立新版本基线，不能静默删除。
不同参数、字段或状态分别作为原子异常：价格边界非法、分页非法、排序非法不能并为一条；不同字段缺失分别记录。原文明示的空查询结果、重复操作等异常条件，不因 HTTP 200 或成功响应而排除。不得为覆盖率挑选或合并条件。
分页中 page 与 pageSize 的异常分别记录。用户已确认：泛指异常分支可以结合同一操作的明确契约展开，纯前置条件不算。例如“查询参数非法，例如……”允许结合该查询的 pageSize 上限具体化，但只有正常 pageSize 约束、没有异常分支时不能生成 C。每条保存 extraction_basis（explicit_named 或 generic_failure_contract）、failure_source_refs 和 contract_source_refs；契约展开必须同时引用异常分支与明确契约，不虚构字段、数值或另一接口的规则。公共入口 minPrice/maxPrice 与下游 priceRange.min/max 保持各自对象。
首次核实后冻结 C 与输入版本；修改分母必须有原文依据及变更记录，历史 37 条不用于本轮验收。
冻结前执行 interaction-checker-audit：只读原文与独立 C，逐条检查异常依据、原子条件、操作绑定、引用及遗漏，不读 G 或测试。正常校验、参数清单、纯前置、普通可选流程不能冒充异常分支；成功处理的原文异常仍保留。全部审查批次完整且无问题后才允许冻结。审查不是生成器的适用性筛选。
有问题时使用 repair-checker-source-audit 保留错误草稿和完整审查依据，让 ecnu-max 对原始包重新抽取，再完整重审；tools 不手工改写或静默删减 C。冻结后的基线禁止原地修补，须建立有原文记录的新版本。
工具同时校验异常分支和契约属于实际层级用例。引用独立接口章节时，operation_binding 保存原文接口标识及本用例正常调用引用，并验证外部契约确属该接口；同一个业务包中出现另一 SR 不能作为授权。

默认 Agent packet 模式，可开最多三个子 Agent。按 packet 合同返回全部已检查 ID；
用 run-agent-batches 可将子 Agent 分工的 packet 交给 ECNU 语义模型处理。
每包一个 C、最多八个同层同业务用例 G 异常，逐对保存全部判定并独立复核接受关系和漏报相关比较。
覆盖比较进一步限定相同原文层级用例 ID，防止一个 RR 下不同 SR 用例互相代替。检查器独立提取该 ID，不从生成模型复制。每个必要条件需给出生成条件中的精确证据或明确缺口，矛盾条件禁止匹配。
比较异常对象、操作、机制和必要触发条件；响应、错误码、处理与恢复不参与覆盖判定。
部分匹配必须识别相同具体异常条件，并说明条件细节缺口；主题或普通操作相同不能匹配。
共享 CLI 负责 ID、批次哈希、完整性、引用和指标校验，不做规则语义匹配。
另一后端是 embedding，阈值必须在输出中记录为未校准参数。

原文覆盖也使用一一匹配：逐对判断完整/部分/未匹配后，由工具最大化配对数并优先完整关系；每个C/G只占用一个对应项，竞争未分配的语义重合另列。漏报率=未分配C/全部C，完整率=已分配G/全部G；RR、SR分别如实报告，合计单独报告，空分母为null。当前只验流程，不设置漏报率通过阈值。
分类识别漏报按 C 标签及实际异常匹配统计；另列标签差异与同类挂载覆盖。未完成或过期批次禁止正式指标。
每轮运行结束自动生成 run_checks.json/md；也可用 check-interaction-run 检查未完成轮次，并显式提供 RR/SR 原文核实文件变化。pending 或 blocked 均不代表指标或验收通过。
完整结果使用 validate-interaction-run 实际执行全量回归与禁用网络的缓存续跑，保存 JUnit、日志、批次前后哈希及重建指标。prepare-interaction-review 绑定本轮实效审查材料；evaluate-generator 校验这些记录与实际 gpt-6-luna/max 审查原始结论。不得以布尔字段代替执行证据。structurally_valid 只表示结构可重建，formally_accepted 才表示全部验收条件通过。
新协议见 references/rr_sr_protocol.md；references/three_roles.md 为历史兼容说明。
