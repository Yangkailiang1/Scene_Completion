# 完整SSD建模

## 输入

当前case-group对应的一组RR/SR正向描述，以及组件身份索引。正文只含这组用例；无全项目异常、测试答案、GT或其他用例。模型侧每行有evidence_id，组件小表提供component_id、名称、组成类型和所属边界。

## 处理流程

1. 整理本用例全部可观察交互。RR描述Actor与整体系统；SR展开原文明示的服务调用。动作可以放入operation.sequence；本地处理不是新增internal_process消息。
2. 每条消息识别发送方、操作、实际数据、接收方，记录顺序、方向和当前层。必须保留明示的逐层返回；对Actor展示业务结果属于可观察输出，不能只提取“进入页面”而丢掉后续交互。
3. 返回parent_id指向本层原请求，端点须完全反向。rr_sr_links只引用消息ID，不能填用例编号；同一RR消息的展开合并到一个sr_ids列表，不交叉占用其他RR的SR消息。
4. 数据仅记录本次传递的字段和位置。API类型、必填性、默认值、通用约束由独立参数任务及属性关联工具补齐；不在此重复抽取。仅本用例额外明确的固定值或规则保留依据，未知项不补造。

## 输出与工具分工

遵守本次模型侧Schema：双方使用component_id，source_refs使用evidence_id，不复制长引文、不重新输出组成分类。程序填case_id、恢复组件身份和真实引文，校验后保存标准JSON；再由工具关联API属性和绘制SVG。模型不写SVG/图像，也不生成异常或复写参数表。

正常情况下每组调用一次；只有校验失败才使用有界修复。材料不足或有冲突时提问/列为待确认，不增加AR生命线，不补造调用关系。
