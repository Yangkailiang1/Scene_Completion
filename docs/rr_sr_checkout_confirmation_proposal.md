# 创建订单的 RR 确认动作与 SR 调用对应

状态：用户已于 2026-10-11 确认“同一次提交”。地址／金额确认作为提交内容细化，映射现有一个 SR 创建订单请求，不新增组件、接口、调用或关注点，不修改原文，不直接生成异常。来源复核应保留这两处原文及步骤，不把同一提交内容强行拆成第二次请求。

当前《系统需求_spec.md》168行触发事件为“顾客在结算页确认提交订单”，170–174行基本流程依次写读取购物车、校验价格库存、顾客确认收货地址和订单金额、调用订单创建接口、锁库存并返回编号。《功能设计_spec.md》对应 SR 基本流程则在现有订单创建请求内完成读取、校验和创建，没有定义第二个确认接口。

来源审计要求把中间确认拆成另一次 RR 请求，并指出目前 SR 地址查询发生在提交之后，不能用它解释更早的用户确认。这是否是独立交互，当前原文没有明确说明。

建议确认口径：中间的地址/金额确认是触发事件“确认提交订单”的内容细化，保留在正常步骤中；在融合 SSD 上归入同一次顾客→商城 UI 的提交交互，映射现有 SR 订单创建流程。不另造第二个 SR 请求、地址查询或接口；也不把后端地址查询解释为提前向用户展示确认信息。

若业务确实是先由系统计算并展示、再让顾客单独确认，应补充明确的 RR 交互、SR 契约和顺序依据，并按已约定流程确认模型或文档调整后执行。不能仅为让来源审计通过而推定第二次请求。
