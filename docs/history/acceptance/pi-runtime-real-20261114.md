## 控制与运行中修正

- 五用例各一个字段绑定、场景生成、语义匹配批次，加原文E架构识别、GT链路/架构识别。RR缺结构化API身份，原文仍有参数与操作语义；不宣称覆盖纯业务文本无接口材料的完整流程。
- 36组配对首次实际请求逐字段完全相同。每次执行新会话、无旧答案复用、最多五次请求。18个批次两轮先跑方全部反转，输入/提示/Skill/Schema/业务规则未变。
- 初版调度使用全局schedule索引与repeat共同计算顺序，导致同批次第二轮未反转。事先记录整体排除规则，安全停在未发起的执行槽；保留第一轮36次，归档已完成第二轮双方12次后重新完成36次第二轮，不按结果筛选。控制暂停没有发起请求。
- Pi SDK内部参数校验会自行反馈错误并继续，原统计只数Python异常会漏计。修正为从实际候选响应序列计算首次通过、修复及拒绝次数；原始日志不改写。回归覆盖SDK内拒绝后成功及提问不算候选失败。
- 一次连接/响应头失败没有返回产物或用量，保守扣账94,342；用户再次明确要求继续1亿Token预算内测试后，记录本实验的继续授权，跳过失败执行、继续独立节点。该第1轮失败请求未重发；第2轮是原计划独立重复，身份不同。正式项目unknown_usage_policy仍为stop。

## 业务核对

66份通过程序校验的产物重新校验全部通过；其中12份仍有本次原文检查表明确指出的问题。核对了51个RR字段声明、138个属性链接、150个字段定义引用、388条固定模板分析及60个场景比较判定。具体实例：

- RR明示Authorization类型及必填，结果仍以缺少接口依据为由遗漏。
- Authorization被绑定到x-service-id和x-merchant-id，并引用服务ID枚举作为凭证字段依据。
- UC-003被挂到UC-001/UC-005依赖边；UC-002没有给定依赖边却被挂载。
- SERVICE价格为0与同商家重名两种独立失败被判partial，产生错误覆盖。

原文核对是Codex依据冻结原文、结构化检查项和失败条件的辅助审查，不是业务专家签字或完备真值；首组绑定故障诊断已知分组，其余使用匿名工作表，也不宣称严格双盲。固定模板规则本身的适用性没有改造。样本仅来自一个合成项目，重复运行按原始批次聚类，不作为独立业务样本。差值探索区间包含0，不证明框架普遍优劣。
