# SSD 三范围比较与业务审核

新执行默认采用 `ssd-case-v1`，结果按交互级、业务链路级和项目架构级三种范围组织。每个结构化用例独立完成“建立 SSD 与三方结果、处理语义对应、展开场景分析、比较与发布”；项目范围再完成“抽取用例依赖与外部服务、独立识别来源、模板分析与补充、比较与发布”。原始文档继续使用现有抽取入口，得到 SSD、接口和实体后进入同一结果服务。风险推荐排序本轮不执行。

## 三种分析范围

- `interaction`：绑定用例 SSD 的发送方、数据和接收方，包含身份、权限、数据、业务属性、CRUD、业务类型和技术扩展关注点。
- `business_chain`：绑定有来源的用例直接依赖边。数据隔离、跨服务数据一致性、调用顺序挂到每条边；级联操作只挂 `relation_type=cascade` 的边。不自动展开间接依赖，同一用例对的不同业务语义分别保留。
- `architecture`：按项目内实际依赖的外部 Service 去重，每个服务一个可用性关注点。人类 Actor 和本地处理不进入架构清单。

三种范围分别展示，指标同时包含关注点层和场景层，并提供项目汇总。未生成的范围显示“尚无结果”，不参与汇总分母。

## 输入、挂载与来源隔离

导入整个 `输入文件` 目录，包含行为模型、功能树、API 提取结果、测试逆向文件，以及最初始的系统需求 spec 和功能设计 Markdown。Markdown 与 JSON 一起保存为不可变输入快照。中间来源继续保留，但“查看原文”优先显示初始 RR/SR 文档。未提供初始文件时明确提示缺少来源，不伪造引用。

IR/SR 同一次失败保留一条、优先 SR 定位；全部原出处都保留。IR 独有异常不会被删掉。字段约束按接口、方向和字段位置动态挂载，业务属性按实体关系挂载，非数据关注点按注册表结构规则挂载。G 不能读取 E/GT，测试不会因 G 没有识别某项而被裁掉。待确认来源在完成业务修正前不计分。

三个挂载目标为发送方、数据、接收方；操作、API、实体及 CRUD 是步骤属性。数据库无 HTTP API ID 的调用、本地 action、请求和返回均保留。

项目依赖与外部服务只从正向原始材料抽取，模型输出必须引用输入已有的原文行。依赖边记录上游/下游用例、关系类型、成立条件、依赖义务、相关实体和出处；外部服务按身份去重，记录职责、技术类型、关联 API、涉及用例和出处。

## 固定参考异常与场景分析

`domain/concern_templates.py` 维护 `three-scope-reference-v1` 参考库。身份认证固定保留无凭证、无效格式凭证、空凭证、Token 无效、Token 过期五类场景；权限固定保留水平与垂直越权。数据库、LLM、业务操作、业务链路和架构范围各自保留完整参考变体。

固定模板由脚本按实际用例、步骤、对象和关注点确定性挂载，保留 `template_id`、`variant_id`、`template_version`、`generation_origin`。字段必填、类型、长度、范围、格式、大小的具体失败条件按实际声明的约束确定性生成，不虚构阈值、状态码或认证机制。

`ssd-generate` 把当前用例、具体步骤、对象、接口、实体、关注点和参考模板发给模型，让模型逐项写“谁在执行哪个操作、发生何种失败、应有怎样的处理”，并允许在同一关注点下补充明确适用且不重复的具体失败。模型不能删除固定模板、新增关注点或更换挂载对象，也看不到 E/GT。模板没有异常原文依据时仍必须分析，不能以证据不足跳过。

每个场景保留 `analysis`、`analysis_origin`、`generation_context`。没有可用模型时固定模板和确定性条件仍保留，待分析项单列；修改步骤后只重新处理受影响步骤的模型分析，人工改写和删除保留。

## 页面编辑

结果页顶部提供“交互级 / 业务链路 / 项目架构 / 项目指标”四个视图：

- 交互级沿用“最终结果 → 用例结果 → 交互对照”：上方选择用例，左侧列出全部 SSD 步骤，右侧按关注点层级分组显示 E / G / GT。关注点与具体场景分别查看，未挂载记录保留在“待定位／本轮不计分”入口。
- 业务链路提供三方对照、业务依赖表、用例依赖图和本层指标；外部服务清单可直接编辑名称、职责、技术类型、关联 API 和涉及用例。
- 项目架构提供三方对照、外部服务清单和本层指标。
- 项目指标按“范围 × 关注点层/场景层”展示分项指标，并展示项目汇总。

交互级支持新增、删除、排序步骤，修改发送方、接收方、操作、数据、API、实体和 CRUD 关联；项目范围支持修改依赖边、外部服务和三方记录。机器原始版、历史修订和当前有效版本分别可查。自动运行只更新机器基线，人工修改和删除作为差量继续应用。并发保存使用 `base_revision`，409 会保留页面草稿并要求刷新。

点击记录“查看原文”打开页内弹窗，支持 Markdown 标题、列表、表格、代码块、章节大纲和引用行高亮。测试原出处与关联需求上下文分别展示。原文中的任意脚本不会执行。

## 离线审核

使用原有顶部“审核交接”，默认一次导出全部用例、业务链路和项目架构到一个 HTML。结果页当前选中对象仅用于定位，不自动限制导出；局部导出在“高级筛选”中显式选择。导出基于已保存修订，有草稿时先保存。

HTML 的“差异审核”仅允许采纳已完成、有效挂载且没有 full/partial GT 覆盖的 G 场景，并填写意见；E/G、四元组与原文只读。“完整参考”提供三层全部关注点、场景及待确认记录，不允许采纳已覆盖或未完成项。即使某层没有可审核项，仍有参考内容与排除原因。原始 RR/SR Markdown 内嵌，离线可阅读、高亮。

离线表格按步骤／依赖／服务及关注点绑定分组，上下文默认折叠；相同原文记录集合共用显示，具体失败条件仍逐条独立采纳和填写意见。已有测试参考与业务采纳预览分别展示。窄屏横向滚动表格，顶部工具栏自动换行。

已有审核 HTML 可用 `scene_completion.review.offline.adoption.render_html(content)` 重新排版并另存副本；该纯函数保留冻结内容、`export_id`、决定和意见，不重新导出项目。浏览器内未保存的审核修改须先保存。

“保存含修改的 HTML”下载包含决定和意见的新文件，重开可继续审核；也可导出 JSON。只上传一个 HTML/JSON 即可预览全部三层，默认勾选无冲突项，点击应用才更新。服务端从冻结 G 构造“业务审核补充”GT，不能通过反馈修改 E/G、原文或上下文。重复导入不重复新增，冲突项保留。应用后刷新各受影响范围及汇总指标，不自动调用模型。

工作台逐条显示审核导出资格和关联 GT。GT 位于其他表格行时提供跨行部分/完整覆盖依据；同一行为空不等于无覆盖。GT 识别执行完成与业务待确认分开：未定位的待确认记录单独保留，仅明确关联的记录可阻断对应范围，不整层排除。

结果页顶部和列操作保持紧凑，四元组／对象详情默认折叠，展开仍可编辑。“专注工作区”可收起项目详情，本地记忆布局；保存和撤销入口保持可见，后台刷新不覆盖草稿。历史报告只读。

## 指标与运行状态

令 `M=G−E`、`T=GT−E`：关注点漏报率为 `(1−|M∩T|/|T|)×100%`，生成有效率为 `|G∩GT|/|G|×100%`。场景诊断单独展示，项目按分子分母求和。空分母显示不适用；未挂载、待确认及未完成项单列。

交互、业务链路和项目架构分别计算关注点层与场景层指标；项目汇总累加各范围分子、分母，不平均百分比。完整重复运行复用验证过的任务输出。单用例失败不阻塞其他用例。历史 mock 输入按其原任务契约回放；新流程 mock 验证显式设置 `workflow_mode: "ssd"`。原协议和历史报告不原地改写。

商业操作幂等性回到实际 C/U/D 交互对象，旧 `global.idempotency` 和 `service.resource_mutation.idempotency` 保留历史识别但停用；读取旧项目冻结注册表不自动迁移，显式采用当前规则时才生成新版本。

## 接口

以下路径均位于 `/api/projects/{project_id}`：

| 接口 | 用途 |
|---|---|
| `GET ssd-results` | 交互级用例版本、分项指标与项目指标 |
| `GET results/{case_id}/editor?revision=original或版本号` | 交互级当前/历史/机器原始结果 |
| `POST results/{case_id}/revisions` | 提交 `base_revision`、编辑后的 `bundle`、可选 `reason` |
| `GET results/{case_id}/revisions` | 交互级修订历史 |
| `POST ssd-review/export` | 可选 `case_ids`、`record_ids`，返回离线 HTML |
| `POST ssd-review/preview` | `content` 为审核 HTML 或 JSON，返回差异/冲突 |
| `POST ssd-review/apply` | `content` 与所选 `case_ids`，应用已预览反馈 |
| `GET project-results` | 两范围可用状态、分项指标和项目汇总 |
| `GET project-results/{scope}/editor?revision=original或版本号` | 项目范围当前/历史/机器原始结果；无结果返回 404 |
| `POST project-results/{scope}/revisions` | 提交项目范围 `base_revision`、`bundle`、`reason` |
| `GET project-results/{scope}/revisions` | 项目范围修订历史 |
| `POST project-review/export` | 可选 `scope`、`anchor_ids`、`record_ids`，返回项目差异 HTML |
| `POST project-review/preview` | 解析项目审核 HTML/JSON，返回差异与冲突 |
| `POST project-review/apply` | `scope` 与 `content`，应用已预览的项目反馈 |

`import-case-result` 同时接受新的 `ssd-case-v1` 与旧 `scene-case-analysis-v1`。旧提交保留原三方结果和匹配，不用新的脚本 G 覆盖原 G。独立脚本使用 `.cac/skills/scene-case-analysis/scripts/case_analysis.py build`。

## 本地验证

运行 `make check` 和 `make frontend-build`。回归覆盖五用例、三范围任务集、固定模板与模型补充、项目依赖与外部服务、原文追溯、IR/SR 去重、请求/响应分离、API 改绑、步骤修订、历史版本、并发冲突、语义判定失效、离线 HTML 保存重开及反馈幂等。离线测试不代表客户模型网关或原生 Windows 已验收。


## 三个范围与参考场景（2026-11-13）

交互级继续使用用例、SSD步骤、五列三方对照、编辑与原文弹窗。业务链路与项目架构沿用相同对照和修订入口，使用真实依赖边及外部服务身份；审核交接选择对应范围导出。历史报告只读。

交互G先按约束和规则挂载固定异常模板：身份认证保留无凭证、格式无效、空凭证、Token无效、Token过期五项；数据范围等有确定值的场景由脚本生成。随后独立ssd-generate任务只读取正向用例、步骤、字段、接口、实体与参考模板，逐项写业务化analysis，可补充适用场景，不能删除模板或读取E/GT。模型业务说明与原始出处、模板血缘分开保存。

项目任务从原始正向RR/SR/AR文档抽取直接用例依赖并保留原文行引用；不展开间接可达闭包，不用同实体CRUD组合猜依赖。同一对用例的不同依赖语义分别保留。每边挂数据隔离、跨服务一致性、调用顺序，只有级联边挂级联操作。项目架构按外部服务稳定身份去重挂可用性。

三个范围分别返回关注点与场景两组漏报率、有效率；总指标累加分子分母。未决来源、未完成模型分析和语义匹配计入完成度缺口。规则变化显式升级任务语义，不改写历史规则与历史成绩。

## 逐格编辑、覆盖与业务采纳（2026-11-13）

RR没有API身份也可运行。保留实际字段，不补造接口；确定关系使用API/服务/方法路径，剩余正向字段定位由ssd-bind处理。请求、响应与存储字段独立；接口约束只附加到实际字段。CRUD保存在operation.kinds，人工指定优先；GET读、DELETE删、PUT/PATCH改，POST根据实际业务语义。修改API或操作后更新自动推导并保留人工覆盖。

三方表与原功能栏保留。点击四元组或E/G/GT文字编辑；空格可补录，表尾选已有框架关注点添加行。单元格可有多条记录，清格仅当前方，整行删除影响三方及关联场景；草稿支持撤销。人工表格行用display_row_id保留，并排不等于已匹配。保存检查base_revision，历史只读，重跑保留人工删除、改绑及修订。

新覆盖口径coverage-any-confirmed-v2：full和partial均覆盖，任一GT可覆盖多条G；每条G只计一次有效。漏报以GT−E中未被G−E覆盖的GT计数；关注点与场景分别统计，汇总累加分子分母。旧历史成绩冻结；保存修订采用新口径，界面显示原始与修订结果。

审核交接导出business-adoption-v2单文件HTML，提供交互、业务链路、项目架构三页。只含有效挂载、已完成GT匹配且无full/partial覆盖的G场景，E不影响导出资格；未完成、待确认相关项排除并计数。没有候选且识别完成的G可以导出。相关步骤的未定位来源阻止该步骤导出；其他未定位来源仍在工作台明确保留。

E/G/四元组/原文只读，GT列仅采纳、撤销采纳及意见。保存HTML后重开可继续；原始Markdown随文件嵌入并支持高亮。回导先预览，由用户应用；服务端校验导出身份，按冻结G创建“业务审核补充GT”，保留G及意见，source_refs不冒充测试，需求来源另存requirement_refs。重复导入不重复新增；有新修订时展示冲突。既有审核格式保留读取，历史报告不开放编辑。

终端接管见 [本地CLI说明](terminal-code-agent.md)。

互斥的明确数值失败（如pageSize=0与pageSize=101）由脚本判不覆盖；partial必须有真实条件重叠或覆盖，不能因字段、关注点或错误码相同就计覆盖。人工修订仍可显式调整判断。

## 单条人工匹配草稿

最终结果中的每个待判定配对提供“确认匹配”和“查看详情”。确认直接建立 `full` 人工判定草稿，卡片立即显示“已匹配 · 未保存”；再次点击“取消本次匹配”恢复点击前的保存状态，不写成“不匹配”。详情保留完整匹配、部分匹配、不匹配及依据编辑，应用后立即回显；取消详情不产生修改。

交互、业务链路和项目架构共用草稿逻辑。计数按相对保存版本发生变化的独立配对计算，同一对反复修改只计一条；其他记录、步骤等内容修改单独统计。已处理的候选卡片保存前保留原位置，待判定数量与步骤导航同步扣减。全部撤回恢复无草稿状态。三方表只叠加人工草稿提示，不自动合并表格行；正式指标在保存后重算，full/partial 均覆盖的口径保持不变。

保存过程中锁定编辑并防止重复提交；保存失败或版本冲突保留草稿。历史版本只读，原始模型判定和人工修订历史继续保留。
