# SSD 交互结果、共用外部服务与业务报告

当前分析范围版本为 `interaction-shared-services-v1`。`scene-workflow-v5` 运行协议、`ssd-case-v1` 用例结构和原命令保持不变。业务链路由测试侧负责：当前流程不再抽取依赖、生成链路异常、执行链路匹配或将链路测试计入漏报分母。旧链路、架构快照及报告保留只读，读取不触发模型或历史迁移。

代码入口、命令和逐字段例子见[从同事材料到离线报告](../architecture/ssd-walkthrough.md)。

## 执行与定位

结构化输入按用例执行 `ssd-prepare → ssd-resolve → ssd-generate → ssd-compare`。原始 RR/SR 文档先转换成相同 SSD。每个成功用例随后触发 `shared-services-merge` 脚本；一个用例失败不会阻塞其他用例发布或服务汇总。

发送方、操作、数据、接收方沿用稳定 step_id。操作属性保存实际 CRUD：人工优先，其次明确声明、语义与 HTTP 方法；GET 为 R、DELETE 为 D、PUT/PATCH 为 U，POST 按实际业务判断。默认结构化流程以 SR 命令为接口身份，RR 可为同号命令补方法和路径。无 RR API 仍可运行。SR 属性按接口 ID、字段名作为发送数据，实体属性按实体引用挂载。

第二层名称为“第二层：功能类型关注点”。当前结构化流程启用 23 项具体关注点。第一层分析输入数据与字段约束，数据库唯一性归字段约束。普通输出数据暂停。确定性范围、类型等数据场景由脚本展开，复杂字段约束由 LLM 结合规则和原文核对。

身份认证与每个 CRUD 操作单位的并发一致性各生成一条 G。认证的五种失败作为条内明细，并发场景描述操作结果冲突。LLM 为固定场景补充业务分析。权限控制分别生成水平、垂直越权。G 读取正向材料，E、GT 各自识别并在对齐时汇入同一 G 行，保留每份失败类型、步骤与出处。不同子条件的 E 与 GT 分别核对。旧报告按保存版本读取。

新版按交互归组第一层输入数据关注点。同一交互的完整性、类型、格式、长度、大小、范围、输入数据有效性、字段约束及特殊字符各最多一项。不同字段的具体失败留在场景层。同一义务由标签、规则或引文重复支持时保留一条场景及全部出处。同一交互和类型的三方关注点可以对应，具体场景分别判断覆盖。

每个 SR 接口路径占位符生成一条特殊字符场景和一条完整性场景。已确认的 CREATE 操作存在输入字段 `name` 时，脚本另生成一条名称特殊字符场景，说明 SQL 注入、HTML 脚本和路径穿越等风险。已明确映射到实体 `name` 的接口字段也适用。如果名称字段就是该接口的路径占位符，沿用同一条路径场景。如果接口与实体的名称有明确对应，则保留两边出处。显式声明的名称字符集和正则继续作为字段约束独立比较。E／GT 依据各自原文，保留实际失败步骤，并分别核对输入对象和失败条件。

## 外部服务先生成，再归并

服务可用性在实际外部请求的接收方生成，不在本地 action、返回或人类 Actor 上重复挂载。项目按同一实际服务身份合并关注点，再按故障类型合并场景。无法确认身份时保留待定位，不靠同名强合并。

三方分别合并后比较。每个合并记录保存成员用例、步骤、原记录及修订、失败条件、业务分析、处理预期、原文引用与成员判定。不同故障不合并；成员中 full/partial 均算已覆盖。工作台“交互级”下分“用例交互”和“共用外部服务”，可展开回到对应交互。原架构结果只作带来源标识的兼容投影。

普通交互按用例计分；可用性副本只在调用处展示，项目按合并单位计一次。项目指标分别累计关注点、场景的分子分母。`coverage-any-confirmed-v2` 允许多对多，full、partial 均覆盖；历史指标冻结。纯展示改名不升级无关模型语义。

## 编辑与原文

保留现有三方表、步骤导航与功能栏，支持逐格编辑、补录、清格、删行、框架关注点补漏和匹配草稿。保存检查 base_revision，失败或冲突保留草稿；重跑保留人工增删改。共用服务修订还检查全部调用成员版本；身份及原始调用由脚本维护。历史视图不可编辑。

每条记录在页内弹窗阅读最初始 RR/SR Markdown，支持格式渲染、章节、行高亮及源码切换。GT 区分测试出处和关联需求，不把需求引用冒充测试来源。

人工新增或修订的记录可在编辑弹窗“来源（原文出处）”中选择本用例快照内的文档、填写起始行与结束行并预览高亮，保存后“查看原始出处”直接跳到对应行。出处按文件自身行号（从 1 开始）计，单条最多 1001 行；引文留空时取所选行原文。手工出处标记 `origin=manual` 并在表格与来源列表中注明“人工补录”。保存校验只接受快照内文档和合法行号，因此不会留下点不开的出处。

结果页出处使用快照文档 ID，导入来源使用各自来源 ID。原文接口对快照 ID 按内容完全一致且唯一的来源文件解析；内容不同或同时存在不同副本时拒绝定位，不按文件名猜测。

Excel 出处在核心文件中使用工作簿的真实相对路径，单独保存工作表及单元格坐标。回读时按指定范围核对引文。同一出处同时保存在异常锚点和来源清单时只展示一次。已有 `xlsx#工作表` 锚点可继续读取，只有行号的旧锚点在整行引文核实后按行高亮。

一条记录常有多个出处，原文弹窗按“RR/SR 在前、其余保持记录顺序”稳定排列，并提供“跳到人工补录出处”直接定位手工引用，便于在众多机器出处中核对人工补充的依据。

## 第二层资源存在性与第一层输入数据有效性

对已绑定接口，URI 路径占位符引用的业务对象按 CRUD 归第二层资源存在性。创建路径由模型区分待创建对象和已有依赖，R／U／D 从路径结构定位。创建对象已存在、查询／更新／删除的目标不存在、父对象不存在和已停用分别形成对应场景。查询集合合法返回空列表保留为正常结果。普通请求字段和实体属性的业务引用仍归第一层输入数据有效性。明确同一约束的出处在资源场景中合并。

## 一个离线业务报告

默认导出 `ssd-business-report-v1`，标题为「异常场景完整性补全识别结果」，注明实际用例数和未完成用例。三项按场景统计，E 提供已有需求的依据。

1. G ∩ 测试逆向：每条被任一 GT 确认覆盖的 G 只计一次。
2. G 有、测试逆向没有：只收已完成识别、生成、匹配且明确未覆盖的 G。
3. G 没有、测试逆向有：只收相关生成、匹配完成且未被任何 G 确认覆盖的 GT。

每项按用例平铺场景和原文入口。场景列包含已确认的失败步骤和具体异常，步骤原文优先于工作台保存的步骤说明。失败位置尚未确认时显示关联步骤。末尾单列共用服务，明确“用例合计＋共用服务＝本项总数”，关联所有调用用例；不增加虚假用例。待确认、未挂载及未完成项单列原因。

在当前 G 义务口径下，场景有效率与报告共用评估资格。相关生成、GT 识别或匹配仍待完成的项先移出相应分母，已确认关系仍可查看。

当前业务报告按用例平铺为三张表。第一项每个用例一行，场景在同一列逐条列出。第二、三项每个场景一行，按用例合并名称和数量。第二项支持按关注点筛选，表内数量随筛选更新，各页总数取完整结果。报告标题、文本、问题归因及解决方案可离线编辑，异常关注点从导出时项目启用的定义中选取，场景数量自动计算并可填写备注。保存 HTML 后可继续编辑，原文仍可离线定位。新报告的编辑保存在 HTML 中，正式结果使用工作台修订。旧审核文件继续使用原有回导接口。

仍读取旧 business-adoption-v2：交互反馈可预览应用，业务链路反馈标记不适用于当前范围；旧架构只读，需重新导出共用服务报告再审核。原内容不会被静默改写。

## 入口与存储

审核交接取 `ssd-review/summary` 预览范围，用 `POST /api/projects/{rid}/ssd-review/report` 取得当前 HTML。历史 `business-adoption-v3` 等审核包继续走 `ssd-review/export、preview、apply`。导出默认全部用例及共用服务，可用 scopes、case_ids、anchor_ids、record_ids、item_ids 精确选择。草稿须先保存，不静默导出旧版本。

- `ssd-results`：用例索引；`results/{case}/editor、revisions`：交互编辑和历史。
- `project-results`：当前交互/共用服务及项目汇总；`project-results/shared_services/editor、revisions`：共用服务修订。历史 business_chain/architecture 的 GET 仍可读，POST 修订被拒绝。
- 共用服务保存于 `shared_service_results/`，不迁移或删除原 `project_results/`、`ssd_results/`。
- 终端 `scene.py --local --data-dir DATA results --project ID --analysis-scope all|interaction|shared_services` 与 HTTP 使用同一服务。接管操作见[终端 Code Agent](terminal-code-agent.md)。

## 验收

执行 make check、前端生产构建、便携资源检查。用真实五用例项目副本验证增量生成、合并与报告回导，17 用例夹具验证动态数量。旧历史与原项目草稿不用于试写；模拟测试不代替真实模型运行，原生 Windows 验收状态单独报告。

## 同事交接的核心 JSON

项目可混用原始 `SysOperation.json`、按目录拆分的 `main-success.json` 以及合并的 `authoring-case.json`。分件文件同目录读取 `existing-exceptions.json`、`extension-mapping.json`、`test-exceptions.json`，项目根目录提供参与者索引 `architecture.json`。导入按用例 ID 决定输入，冲突用例可独立排查。

默认使用 `scene.py core-input inspect → convert → validate`。独立分析工具仍提供兼容命令 `export-core`。输出可直接重新导入，并包含 `source-map.json`。清单中的 `file` 与 `json_pointer` 指向导出时读取的原输入。四元组由发送方、接收方、操作和数据组成。命令模式由 `data_obligations` 引用 SR 字段，`steps[].entities` 单独关联实体。实体异常用 `entity_id`、`attribute` 标识，当前结构化流程的接口异常用 `parameter.command_id` 和 `parameter.name` 标识。扩展映射一条对应一个测试扩展，`bindings` 记录已确认的独立挂载。

E 和 GT 独立导入，保留实际失败步骤。场景比较先按请求边界、对象和失败条件筛选，确定等价的候选直接匹配。对于同一人类 Actor 请求，来源明确描述的凭证缺失、为空、格式非法、校验失败或过期，在 G 包含相应失败类型且拒绝预期一致时，直接匹配同一认证场景。尚有语义差异的候选由模型比较。模型的状态和理由明确矛盾时仅复核受影响的候选一次，仍矛盾的配对标记为「匹配未完成」。同用例同实体同属性的约束在不同行可以相互对应。当前结构化流程按接口 ID 和字段名区分输入字段，交互双方和步骤仍由 SysOperation 决定。当前规则自动生成 CRUD 功能类型关注点，展示、分析生成、发布功能类型暂不生成。第四层自动挂载外部大模型响应解析失败，存量数据有效性保留定义。数据库特殊字符退出新版范围。未提供 GT 时生成结果可查看，相关覆盖指标标为未评估。

同一用例中，同一外部大模型的响应解析关注点挂在首个请求上。主成功流只有模型返回时，挂在首次返回步骤的发送方。结果保留全部调用和响应步骤及其出处。没有明确响应契约时生成一般解析失败。明确要求 JSON 或规定响应必填字段时，分别生成 JSON 语法失败或必填字段缺失场景。E／GT 从各自来源识别同一服务的响应异常，允许对齐到此前的挂载步骤，保留实际失败位置。响应解析按用例计入交互结果，共用外部服务仍汇总可用性。

当前核心 JSON 的 `interface_field_policy=sr-input-by-name-v1` 表示 SR 每项 `attributes` 都是该命令发送的数据字段。依据 `tags`、`constraints` 及其出处生成校验，字段无需填写位置或方向。`main-success.data_obligations` 记录 `step_id`、`field_id`、`command_id` 和 `name`。字段约束出处继续使用原文行号或 Excel 坐标。同一接口的重复声明合并出处，确有冲突的字段单列待确认。仅描述返回值本身异常的 E／GT 属于范围外，非法输入后返回错误仍纳入输入校验。已保存的旧报告保留原字段及计分，重跑时迁移能唯一对应的人工修订。

当前结构化流水线比较节点发布 `coverage-g-obligation-v3`。E 和 GT 分别识别，再按最终 G 的关注点与场景义务对齐。每条 G 独立成行，一个格子汇总本方证据和去重后的出处，保留原记录和实际失败步骤。一个来源可命中多条不同 G；同一义务里的多份证据只计一次。无对应 G 的有效记录独立显示，未能定位的记录留在待定位区。新判定只有匹配和不匹配，旧报告读取冻结口径。

「参数校验失败」仅匹配同一接口的适用请求校验义务，「参数格式非法」限定到字段格式，「非法 JSON」限定到请求体解析。已明确定位到接口、缺少对应 G 的概括性请求异常挂到接收方的输入数据关注点。数值边界条件分别匹配，`page > 100` 不覆盖下界。可在任一 G 行解除单条证据关系，原出处及同一证据的其他匹配仍保留。



## 命令四元组

默认 `core-input convert` 创建 `command-interaction-v3` 核心目录。每个 SR 接口只在一个主调用步展开，关联它操作的实体与实际 CRUD。等价的接口及实体约束保留双方出处，其他出现步骤只保留引用。多个 CRUD 的同类第二层关注点在同一接口内合并。外部服务的第二层按用例、服务与 CRUD 分别展开，在每种操作的首个实际调用处挂载。后续同类调用及其校验、响应继续作为来源和 E／GT 对齐范围；同一组调用上的多种 CRUD 可以合并相同模板。已经保存的旧用例通过定向重跑更新挂载。

原文 E 和测试 GT 各凭本方来源和主成功交互分类。G 生成完成后，再结合分支条件、失败步骤提示、参与者和最终 G 分别对齐。一个宽泛来源可关联多个具体场景。原文明确独立的失败分别统计，概括性记录保留同一身份。没有兼容 G 时按来源独立挂载。匹配保留来源实际失败步骤及 G 主挂载步骤，支持跨步骤回查。没有原文行号时可查看行为模型分支与 JSON Pointer。能确认对应 G、但无法确认实际失败步骤时，单列失败步骤待定位。身份认证与权限控制只挂载在人类 Actor 发起请求的发送方。服务间身份与权限证据保留原始出处，归为范围外，不参与当期匹配和计分。

同用例按 `apiId` 合并 RR 方法与路径和 SR 字段。缺少确定性调用证据时由模型选择，无法唯一定位则保留首步回退及待确认原因。旧快照按保存版本查看。升级已有用例可定向重跑，工作台会提示无法沿用的修订。
