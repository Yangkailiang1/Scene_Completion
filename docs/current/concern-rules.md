# 当前SSD关注点与计分边界

本页整理当前代码和已确认规则，不新增算法。任务执行以项目冻结的注册表、当前Schema及语义版本为准；[v9/v10/v11历史记录](../history/scene-workflow-v5/)保留当时实现和验收数字，其中详细流程的全局分析、推荐和旧证据门槛不自动成为SSD主流程规则。

## 输入、定位与隔离

发送方、数据、接收方是三个挂载目标。步骤另存操作、API、实体、CRUD、方向和请求/返回关系。实际调用、本地action、请求和返回分别定位；更改显示名称或排序不改变稳定步骤ID。不同实体、字段、方向和实际调用不因名称相同而合并。

G仅从正向SSD、接口、实体及规则生成；E与GT根据各自原始材料独立识别。IR/SR同一次失败去重时SR优先，保留双方出处；IR独有失败继续保留。正常、成功备选、待确认和未挂载记录不进入确定计分集合。

## 挂载规则

数据关注点按实际字段及声明的必填、类型、范围、格式、长度等约束挂载，枚举归数据范围。请求与返回分别使用自己的字段；接口字段不因同名自动变成存储字段。上下界等独立失败条件按现有规则展开。

非数据关注点按注册表中的参与者、请求方向、CRUD、技术类别和实体关联规则挂载，不再附加“原文明确写出该关注点才挂载”的门槛。真实人类请求使用人类profile；外部Service真实调用挂接可用性；Service关系、CRUD及技术类别按相应profile处理。LLM技术规则无需补造CRUD。具体启用键以注册表和项目有效定义为准。

跨属性业务条件保持完整关系，不能拆成两个普通字段范围。成功响应中的业务关系与数据库实际执行业务规则分别定位：响应约束归实际返回发送服务，数据库检查归其执行步骤。`productType=SERVICE`时`price>=1`与price普通数值范围是不同规则；数据库拒绝请求后传播的错误响应不自动成为额外的成功输出违例。E/GT只使用自身材料描述的失败，不从G补答案。

本轮不执行全局关注点、全局幂等性或风险推荐排序；运行解释时停用已迁到全局的旧交互幂等键，原用户JSON和历史报告不被改写。

## 比较、指标和修订

三方先按SSD对象关注点定位，再比较独立失败条件。一个失败场景可以关联多个关注点；不同两两匹配不通过传递关系自动补计命中。完整、部分、不匹配与待比较分别保留。

令`M=G−E`、`T=GT−E`，关注点漏报率为`(1−|M∩T|/|T|)×100%`，生成有效率为`|G∩GT|/|G|×100%`。项目汇总分子分母，空分母显示不适用。场景诊断独立展示；关注点漏报率为0不代表全部场景覆盖。

人工修订保存为新版本，旧机器结果和原始出处继续可查；改动步骤、字段或条件使相关旧语义判定失效，未决范围明确列出。没有模型完成比较时不能伪装完整评测。执行节点全部通过与业务审核全部确认分别展示。

实现入口为`analysis/ssd/pipeline.py`、`domain/ssd/`和`application/ssd_revision_service.py`，页面操作见[SSD三方比较与审核](ssd-case-workflow.md)。
