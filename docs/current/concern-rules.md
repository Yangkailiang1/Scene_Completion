# 当前SSD关注点与计分边界

本页记录2026-11-16确认的交互与共用服务规则。任务执行以项目冻结的注册表、当前Schema及语义版本为准；[v9/v10/v11历史记录](../history/scene-workflow-v5/)保留当时实现和验收数字。稳定定义ID和原有`layer`不改写，范围由`scope`明确区分。

## 当前范围

当前版本 interaction-shared-services-v1 只分析交互，业务链路由测试侧负责，不进入本方法的生成、匹配或漏报分母。外部服务可用性在实际调用处生成，三方分别按实际服务与故障合并后比较；普通用例指标排除调用副本，项目只累加共用单位一次。第二层展示名为“第二层：功能类型关注点”，CRUD 规则不变。旧链路、架构及指标快照只读。

## 输入、定位与隔离

发送方、数据、接收方是三个挂载目标。步骤另存操作、API、实体、CRUD、方向和请求/返回关系。实际调用、本地action、请求和返回分别定位；更改显示名称或排序不改变稳定步骤ID。不同实体、字段、方向和实际调用不因名称相同而合并。

G仅从正向SSD、接口、实体及规则生成；E与GT根据各自原始材料独立识别。IR/SR同一次失败去重时SR优先，保留双方出处；IR独有失败继续保留。正常、成功备选、待确认和未挂载记录不进入确定计分集合。

## 挂载规则

数据关注点按实际字段及声明的必填、类型、范围、格式、长度等约束挂载，枚举归数据范围。请求与返回分别使用自己的字段；接口字段不因同名自动变成存储字段。上下界等独立失败条件按现有规则展开。

### 用例内实体约束的挂载位置

功能树按用例划分，每个用例声明自己的实体；约束只取本用例声明的实体，不跨用例取并集。每个实体约束恰好挂载一个步骤：

- 该用例存在针对该实体的**具体校验步骤**（`step_kind=action` 且正文或声明数据点明该实体）时，挂在该校验步骤；
- 没有该类校验步骤时，挂在用例的**首个业务请求**（step1）；
- 同一实体存在多个无法区分的校验步骤时保留待确认，不静默取第一个；
- 透传的中间层不挂载，因此同一字段经多个报文传递仍是一个关注点。

约束规范化在 `analysis/concerns/constraint_atoms.py` 中确定性完成，识别不了的规则保留在 `unresolved` 中，不再落入通用 `other` 被丢弃。原文只写上限符号而未给数值（如“长度≤N”）时，仍生成对应关注点，数值留空并标注待补，不编造数字。跨字段关系（如“0 ≤ 且 ≥ sale_price”）保持整体，不拆成两个字段范围。

非数据关注点按注册表中的参与者、请求方向、CRUD、技术类别和实体关联规则挂载，不再附加“原文明确写出该关注点才挂载”的门槛。真实人类请求使用人类profile；Service调用认证与授权、CRUD及技术类别按相应profile处理。LLM技术规则无需补造CRUD。数据有效性仅在字段有实际资源引用关系时挂载，不能仅凭字段名称含Id认定。

创建、更新、删除分别挂载并发一致性、幂等性、对象资源存在性。幂等性恢复到实际C/U/D交互对象，不再同时生成`global.idempotency`；旧通用`service.resource_mutation.idempotency`只保留历史识别。查询不强制套用变更幂等性。已明确的本地幂等校验可定位回实际入站调用。读取旧项目冻结注册表不自动迁移；显式采用当前规则时才生成新版本。

跨属性业务条件保持完整关系，不能拆成两个普通字段范围。成功响应中的业务关系与数据库实际执行业务规则分别定位：响应约束归实际返回发送服务，数据库检查归其执行步骤。`productType=SERVICE`时`price>=1`与price普通数值范围是不同规则；数据库拒绝请求后传播的错误响应不自动成为额外的成功输出违例。E/GT只使用自身材料描述的失败，不从G补答案。

## 固定参考模板与模型补充

`domain/concern_templates.py`维护`three-scope-reference-v1`参考库。身份认证固定保留无凭证、无效格式凭证、空凭证、Token无效、Token过期五类场景；权限固定保留水平与垂直越权。数据库、LLM和业务操作采用各自完整参考变体；业务链路模板退出当前执行。

每个G场景保留`template_id`、`variant_id`、`template_version`、`generation_origin`。固定模板来源为`reference_template`，具体字段范围和实体条件的确定性展开为`deterministic_constraint`。模型可基于允许的正向输入补充具体场景，不能删除固定模板，也不能从E/GT或匹配答案补写G。模板不给未声明的超时秒数、HTTP状态或Token格式；业务属性具体唯一、不可变和组合规则仍绑定实际实体约束。

项目范围的E/GT原始记录放在各通道`project_records`中，保留稳定ID、用例、原始内容和出处，只保留历史追溯，当前不再调度业务链路识别。它们不再作为“本轮不计分”的交互pending，也不混入交互指标。

## 比较、指标和修订

三方先按SSD对象关注点定位，再比较独立失败条件。一个失败场景可以关联多个关注点；不同两两匹配不通过传递关系自动补计命中。完整、部分、不匹配与待比较分别保留。

令`M=G−E`、`T=GT−E`，关注点漏报率为`(1−|M∩T|/|T|)×100%`，生成有效率为`|G∩GT|/|G|×100%`。项目汇总分子分母，空分母显示不适用。场景诊断独立展示；关注点漏报率为0不代表全部场景覆盖。

人工修订保存为新版本，旧机器结果和原始出处继续可查；改动步骤、字段或条件使相关旧语义判定失效，未决范围明确列出。没有模型完成比较时不能伪装完整评测。执行节点全部通过与业务审核全部确认分别展示。

规则展开见`workflow/ssd/generate/`，匹配与计分见`domain/ssd/`，结果保存见`application/ssd_revision_service.py`。页面操作见[SSD三方比较与审核](ssd-case-workflow.md)。

当前coverage-any-confirmed-v2中full与partial均计覆盖，每条G被任一GT覆盖计一次，允许一条GT覆盖多条G；互斥数值或上下界失败不是partial。关注点与场景均按此口径计算；旧版无policy标记的历史保留一对一完全匹配口径。
